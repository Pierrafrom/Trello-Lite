## Project summary

The **SAE 2 - 1256** project consists of building a Trello-like application
using the *Java* language and the *Java Swing* graphical library. The
application manages projects, tasks, and users. We started with a project
management study and a UML design study, then built the application
itself following the **Model-View-Controller** pattern taught in class.

## Explanation of our MVC

For this project, we were strongly advised to follow the **MVC** pattern.
We split the application into three separate packages: the model, the
view, and the controller. The **model** manages and processes the data.
The **view** displays the application and the serialized data. The
**controller** manages interactions between the application and the user
through events. Buttons are displayed in the **view**, but are wired to
listeners and events that live in the **controller**, as the **MVC**
convention requires. All three parts are independent from one another,
but are tied together through their methods and through the
*TrelloMain* class. We also added a **style** package containing the
classes that manage the application's styling.

## Building the application

### Model and project setup

The first step was to retrieve the code auto-generated by *Visual
Paradigm* during the **UML** phase of the project. That part was fairly
simple: once the code was generated, we implemented the functions
planned during the analysis phase, in other words the **model** layer.
This wasn't particularly difficult given how simple the required
functions were: mostly *getters* and *setters*, or *add*/*remove*-style
functions. For example:

```java
public ArrayList<Card> getCards() { return cards; }

public void addCard(Card card) { cards.add(card); }
```

### Setting up git

Since the step above didn't require the whole team, we set up a *Git*
repository to simplify the rest of the work: one repository, and **one
branch per team member**. From then on, every code change happened on
each person's own branch, then got pushed to that branch and to main so
everyone had the right version. Pulling in someone else's work just
meant merging their branch into main and staying up to date. This made
collaboration much easier: nobody had to worry about which version of
the code they had, and everyone could work in parallel without issues.

### View

Once the model was written and working, the second step was building the
graphical interfaces, the view layer. We started with plain *JPanel*
components straight from Java Swing. After implementing a few of them, we
realized it would help to have some visual consistency across views.

So we created classes that directly implement the *Java Swing* classes
but already carry attributes like color and font. To make this even more
modular, we defined an **interface** holding the colors and fonts,
implemented by the classes that manage styling. This gives us cleaner,
easier-to-modify code: to change a color used across cards, lists, and
boards, we only need to change one value in the interface instead of
editing every class by hand. All of these classes live in the *style*
package, kept separate from the views that are actually rendered on
screen.

### Controller

Next, we needed to wire controllers into the graphical interface. We
built the controllers required for the application to work correctly,
each one running checks such as verifying that a new board's name isn't
null, or that a workspace being deleted actually exists. This kept the
application free of inconsistencies and errors. Creation and deletion
controllers open a new window telling the user what to do next, and
flagging any input error.

## Testing

While coding, we regularly needed to test our functions and displays. To
do that, we created **temporary `main` methods** inside the classes under
test.

Views were fairly simple to test since the rendered output directly told
us whether something worked. For example, testing a card list display
just meant building a card list and rendering it: if the display looked
**correct**, we moved on; if it wasn't **perfect**, we knew the code
needed changes. Here's an example test `main` for rendering a card list:

```java
public static void main(String[] args) {
	CardList cardList = new CardList("Test");
	Card card1 = new Card("Card 1");
	Card card2 = new Card("Card 2");
	Card card3 = new Card("Card 3");
	cardList.addCard(card1);
	cardList.addCard(card2);
	cardList.addCard(card3);
	CardListView cardListView = new CardListView(cardList);
}
```

Testing the **controllers** was fairly simple too, since the views were
already built: we just wired the controllers to the buttons and checked
whether the resulting actions were **correct**. For example, testing the
controller that creates a new workspace just meant clicking the
corresponding button and checking that the workspace was created with
the right information displayed. As for the style classes, since they're
used across every view, any problem showed up immediately, so no
dedicated testing was needed there. The model classes, being simple as
described earlier, didn't need particular testing either: there's little
room to get a *getter* or a *setter* wrong.

## Additional details

### Conventions

For this project, we used standard Java naming conventions for cleaner,
more readable code: class names start with an uppercase letter, variable
names with a lowercase letter, matching most Java conventions. We also
decided to write the application **entirely in English**, to keep the
code unified and avoid the "*Franglais*" we might otherwise have ended up
with by coding in French.

Here's a summary of the naming conventions we used throughout the project:

| Type | Convention | Example |
| --- | --- | --- |
| Classes | UpperCamelCase | Card |
| Interfaces | UpperCamelCase | MyStyle |
| Methods | lowerCamelCase | getCards() |
| Variables | lowerCamelCase | firstName |
| Constants | UPPER_CASE | HEIGHT |
| Packages | lowerCamelCase | views |
| Enums | UpperCamelCase | Role |
| JSwing variables | lowerCamelCaseType | titlePanel |

We also made a point of documenting the code thoroughly with Javadoc:
every method, even a very simple one, gets a comment block explaining
what it does, its parameters, and its return value. This makes the code
much easier to understand. These comments follow this structure:

```java
/**
 * This method does something
 * @param param1 ,type, this is the first parameter
 * @param param2 ,type, this is the second parameter
 * @return ,type, This is what the method returns
 * @author name of the author of the method
 * @see related type, method, class, etc...
 */
public type methodName(type param1, type param2) {
	// Code of the method
}
```

Finally, to make the code even more readable, each "section" of a class
is broken into blocks, separated by **comments**. For instance, in a
*Card* class, we have a block for attributes, one for constructors, one
for getters and setters, and so on. This keeps the code more readable
and easier to modify. Here's an example:

```java
// -----------------------------------------------------
// ATTRIBUTES
// -----------------------------------------------------
private int id;

// -----------------------------------------------------
// CONSTRUCTORS
// -----------------------------------------------------
public Class() {
	// Code of the constructor
}

// -----------------------------------------------------
// GETTERS AND SETTERS
// -----------------------------------------------------
public int getId() {
	return id;
}
```

### Data serialization

So users can save their data between sessions, we had to **serialize**
the application's objects: turning them into a byte stream that can be
saved to a file. We implemented this after building the views, so we
could both verify the views worked correctly and get concrete feedback
on the serialized objects. Later on, we needed to modify the serialized
objects to add features or fix bugs, and ran into a problem: serialized
objects aren't **backward compatible**. Modifying a serialized object and
then trying to deserialize an older version throws an error. After some
research, we found that the *JVM* automatically generates a
*serialVersionUID* for each serializable object, unique to that object,
used to check whether the serialized object matches the one being
deserialized. If it doesn't match, deserialization fails. This
*serialVersionUID* is generated automatically by the *JVM* based on the
object's members, their types, implemented interfaces, methods, and so
on, so it changes any time we modify the object even slightly, like
adding a single attribute. This caused repeated problems whenever we
changed a model class, so we decided to define the *serialVersionUID*
for each model class ourselves instead of relying on the JVM's default.

### Participants

When you launch the application, a login window opens. You can either
**log in** or **sign up**. If you don't have an account yet, sign up by
filling in the requested fields. Once registered, your own workspace is
created automatically. If you already have an account, log in with your
email address and password.

When you add a participant to a workspace, if they already have an
account, they're added based on their email address alone. Otherwise,
a new account is created with the information provided, including a
password.

### Roles

Every user of the application has an assigned role. There are three
roles: **Admin**, **Member**, and **Observer**, each with different
permissions and different levels of control over a workspace.

An **Admin** has full control over the workspace: renaming it, adding
members, adding boards, editing cards, and so on. A **Member** can edit
boards by adding card lists, renaming boards, or editing cards. An
**Observer** has no power over the workspace at all: they can't modify,
add, or delete anything.

Each participant's role is unique to each workspace, meaning person *A*
can be an **Admin** on workspace *1* but a plain **Observer** on
workspace *2*. This allows for finer-grained permission management based
on each project and each person's responsibilities. When a participant
creates a new workspace, they're automatically added as its creator, so
they can then set it up and add the right members. Anyone, including
**observers**, can create a workspace: there would be no reason to
prevent someone from creating their own workspace.

### Possible improvements

After many hours of planning, project management, and hands-on coding,
we ended up with a working Trello-like application, and we're genuinely
**satisfied** with what we built. That said, we know it isn't perfect,
and we have a few ideas for how to improve it:

- Improve the **design**, especially the combo boxes we used heavily:
  they're simpler to code and display since they're a single block, but
  can be awkward to navigate.
- Support **archiving cards** and card lists, so completed cards and
  lists could be retrieved later, for reference or to undo a validation.
- **Optimize the application** per operating system: the login window
  works correctly on macOS but unfortunately doesn't display properly on
  Windows.
- Handle participant information more carefully: validate email address
  structure (or send a verification email), require special characters
  in passwords, and hash passwords for better security.

### Package

Here's the file structure of the application:

```
Trello-Lite
├───rapport.md
├───README.md
├───docs
├───data
|   └───datas.ser
├───src
|   └───trelollite
│   	├───controller
│   	├───model
│   	├───style
│   	├───view
|       └───TrelloMain.java
```

We chose to place *TrelloMain.java* inside *src*, since it's used by a
large part of the other files: keeping it inside the *trellolite*
package gives every other file easy access to it.

### Reports

This project comes with a single report available in two formats: *.md*
and *PDF*. The *.md* version is available directly in the project
package, and the *PDF* version is in the project submission. We chose
both formats so everyone can pick what suits them: *.md* is easier to
edit while coding, and *PDF* is easier to read. Since we're also
publishing this project on GitHub, the *.md* format displays nicely on
that platform too.

### Visual Paradigm

During the project, we realized our original plan didn't quite match
what we had designed earlier in UML. We revisited the UML diagrams
partway through the project to reorganize ourselves better, which gave
us a clearer overall picture and helped us make better decisions about
who should do what and when.
